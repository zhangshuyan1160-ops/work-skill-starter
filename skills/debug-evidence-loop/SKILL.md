# 有验证依据的调试

将故障现象、根因假设、修改和验证联系起来。流程规模随问题复杂度变化，遵守当前项目约定和用户指定的修改范围。

## 定位与修复

1. 读取相关项目说明与当前工作区状态，明确预期、实际现象、错误信息及环境。保护已有未提交修改；复现应在合适的测试或隔离环境进行。
2. 找到最短的有效复现或现有失败检查，并检查近期相关变更。无法复现时说明已观察到的事实及缺少的证据，先做可开展的静态定位。
3. 提出可被证据区分的根因假设。优先做能排除假设的小检查，一次改变一个关键因素。跨服务问题检查失败边界及输入输出，日志只收集诊断所需信息。
4. 根据证据修改最小相关范围，并用原复现验证。行为回归适合增加能失败的针对性测试；低影响文本修改不机械增加测试。
5. 运行与改动有关的回归、构建或其他项目必需检查。记录命令、环境和结果；检查通过后，只有新变更或新疑点才重复验证。
6. 多次尝试没有缩小不确定性时重新检查假设和接口边界，改变调查方式。是否暂停取决于真实阻塞或额外授权需求，不能仅因达到某个尝试次数就放弃可继续的工作。

## 交付

说明修复了什么、根因证据是什么、改动在哪里、实际验证了什么以及剩余限制。分别表述已修改、针对性检查通过和完整检查通过。

如果环境或依赖阻止验证，交付已有定位与修改，并准确写“未验证”；不能把代码看起来合理、静态检查成功或旧测试记录说成本次运行通过。已有验证证据且代码未改变时可引用，不为重复同一句结论重跑。

按用户已授权的范围完成代码工作；发布、部署、外部通知等动作依照用户的实际要求。无需为常规可逆的定位与修复重复请求许可。

## 核对

- 结论能对应日志、复现或代码证据；假设没有被直接写成已证实根因。
- 原始故障路径得到验证，测试范围与报告的成功范围一致。
- 没有混入无关重构、忽略失败检查或覆盖用户修改。

示例请求：“这个接口在本地正常、CI 报错。请定位原因，修复后给出实际验证结果。”
